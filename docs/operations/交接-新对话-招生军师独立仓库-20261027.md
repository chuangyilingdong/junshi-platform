## 2. 拆仓目标与非目标

### 目标

1. 招生军师拥有独立 Git 仓库、独立依赖、独立测试和独立发布节奏。
2. 招生军师的改动不再和网站后台、作品广场、机构/学生平台混在同一条分支。
3. 服务端 `/api/junshi/*` 可以由独立进程承载，客户端仍访问 `https://aicyld.com`。
4. 新仓库不包含明文密码、Provider Key、OSS Secret 或生产环境私密配置。
5. 保留现有客户端版本、更新地址和业务接口，先做“代码和进程拆分”，不强制同时做数据库拆分。

### 非目标

- 第一阶段不拆 MySQL 数据库。
- 第一阶段不重写登录体系。
- 第一阶段不改客户端 API Base、`/api/junshi/*` 路径和返回格式。
- 第一阶段不迁移网站旧 `/junshi` 网页 UI。
- 不在新仓库里复制整套网站平台基础设施。
- 不在没有验收和用户确认的情况下自动发布、自动改 Nginx 或自动切生产流量。

## 5. 服务端耦合清单

这是拆仓最容易出问题的地方。`junshiWorkbench.js` 并不是孤立模块，当前至少依赖：

```text
../lib.js                        数据库、鉴权、错误、CORS、ID、时间
routes/billingConfig.js          AI Provider 策略、计费/套餐配置
routes/aiGeneration.js           Provider Selection / generation options
services/generationProvider.js   Provider 客户端
services/providerContract.js     Provider 错误和 mock 判定
services/providerSecret.js       Provider Key 读取
config.js                        AI Provider 默认 Key 等配置
services/fileUploadSecurity.js   上传大小、multipart、文件落盘
services/fileStorage.js          OSS/本地存储、签名/跳转、删除对象
services/complianceEngine.js     合规规则和审读
```

`apps/server/src/index.js` 还直接：

```js
import { handleJunshi } from './routes/junshi.js'
```

并在启动时调用：

```js
const { initJunshiPeerAutoScheduler } = await import('./routes/junshiWorkbench.js')
initJunshiPeerAutoScheduler()
```

因此：

1. 不能只复制 `apps/server/src/routes/junshi*.js`；
2. 不能直接复制整个 `apps/server` 再改端口；
3. 应把最小能力抽成 `packages/platform-core` 或明确的适配器接口；
4. 新 API 不应通过深层相对路径反向 import 网站主服务。

### 平台能力的处理优先级

| 能力 | 第一阶段建议 |
|---|---|
| MySQL 连接 | 共享现有库，隔离读写 `junshi_*` 表 |
| 机构登录/会话 | 共享现有登录体系，保留 cookie/token 和角色语义 |
| 文件上传/OSS | 共享现有存储桶和访问策略，新 API 只持有运行时配置 |
| AI Provider | 共享 Provider 选择和密钥注入方式，不复制密钥 |
| 合规规则 | 随 `data/junshi` 和 `complianceEngine` 进新仓库 |
| 抖音 Worker | 随新 API 进新仓库 |
| 计费/权益 | 第一阶段保留现有策略；若无法抽成接口，列为 cutover blocker |

### 登录边界

新 API 至少需要得到：

```text
owner_key = org:<机构 id> 或 user:<用户 id>
org_id
role（ORG_ADMIN / TEACHER / SUPER_ADMIN 等）
会话是否有效
```

但不要把登录实现重写成另一套。推荐：

- 先复用现有登录 cookie/token 和同一机构身份；
- 把验证逻辑放进 `platform-core` 的 auth adapter；
- 新 API 只依赖 adapter 暴露的 `requireAuth` / `requireRole` 语义；
- 不把用户密码、cookie 明文、Provider Key 写入仓库。

## 6. 第一阶段上线架构

```text
Electron 客户端
      |
      | https://aicyld.com
      v
    Nginx
      |-- /api/auth/*      -> 现有网站主服务
      |-- /api/junshi/*    -> junshi-api 独立进程
      |-- /downloads/*     -> 现有静态下载目录
      |-- /admin/*         -> 现有网站后台
      |-- /org/*           -> 现有机构平台
      |-- /junshi/*        -> 现有网站静态页（暂时冻结）
                              |
                    同一 MySQL（初期）
                    同一 OSS/文件存储
                    同一 AI Provider 配置注入
```

关键原则：

- 客户端仍使用 `https://aicyld.com`，先不改 API Base；
- `/api/junshi/*` 的路径、方法、请求体、响应体、SSE、错误码保持兼容；
- `/api/auth/*` 仍由网站主服务负责；
- 新 API 独立启动、独立重启、独立看日志；
- 先做路径分流，不做域名拆分；
- Nginx 路由必须可回滚到旧平台服务。

## 9. 风险与回滚

### 高风险点

1. **鉴权语义变化**：机构、老师、超管角色判断不一致会导致 401/403 或跨机构数据问题。
2. **计费/Provider 策略漂移**：新 API 自己复制一份策略，后续会出现两套规则。
3. **存储路径不一致**：上传成功但下载 404，或 OSS object key 变化。
4. **数据库连接池和事务**：独立进程连接同一 MySQL 后，连接数、锁等待和迁移顺序要重新评估。
5. **后端长任务**：抖音采集、ASR、数字人轮询在进程重启时会丢失或重复提交。
6. **Nginx 分流错误**：`/api/auth/*` 被错误代理到 Junshi API，或旧 `/junshi` 页面请求新 API 时契约不一致。
7. **收费任务重复**：真实 AI/数字人测试必须设上限，验收后清空测试数据。

### 回滚策略

- 保留旧网站主服务原进程和原路由。
- 保留旧 Nginx 配置副本。
- 新 API 通过独立 systemd unit 运行，回滚只需切回 Nginx upstream 并停止新 unit。
- 数据库第一阶段共享，不做破坏性 schema 变更；新表变更先写迁移和回滚 SQL。
- 不在切流同一次操作中删除旧代码。
